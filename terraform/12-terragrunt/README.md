## Mental Model

> Terraform is a great tool but it has one fundamental problem at scale: **everything that should be different between environments must be repeated** — backend config, provider config, module source URLs, input variables. Terraform has no native answer to DRY infrastructure configuration. Terragrunt is that answer.

Terragrunt is a thin wrapper around Terraform. It does NOT replace Terraform — it calls Terraform internally. Every `terragrunt plan` eventually becomes a `terraform plan`. What Terragrunt adds is a **configuration layer on top of Terraform's configuration layer**.

```
Your terragrunt.hcl
      ↓  (Terragrunt pre-processes)
Generated .tf files (backend.tf, provider.tf) + downloaded modules
      ↓  (Terragrunt calls)
terraform init → terraform plan → terraform apply
```

## How Terragrunt Modifies the Execution Model

When you run `terragrunt plan`, Terragrunt performs these steps **before** Terraform runs:

### Step 1 — Source Download (`.terragrunt-cache`)
If the `terraform { source = "..." }` block points to a remote URL (Git repo, registry module), Terragrunt downloads it into a `.terragrunt-cache` directory next to your `terragrunt.hcl`.

```
live/prod/app/
├── terragrunt.hcl           ← you write this
└── .terragrunt-cache/       ← Terragrunt writes this (add to .gitignore)
    └── <hash>/
        └── <hash>/
            ├── main.tf      ← downloaded from remote module source
            ├── variables.tf
            └── backend.tf   ← generated by Terragrunt generate block
```

**Caching**: once downloaded, Terragrunt will NOT re-download unless the source URL changes or you pass `--source-update`. Use `--source ../../../modules//app` for local development to point at a local copy.

### Step 2 — File Generation
Terragrunt executes all `generate` blocks in the `terragrunt.hcl` file hierarchy (the unit's own file + all parent `include`d files). Common generated files:

- `backend.tf` — remote state config (S3 bucket, DynamoDB table, key path)
- `provider.tf` — AWS provider with account-specific `assume_role`

### Step 3 — Terraform Execution
Terragrunt `cd`s into the `.terragrunt-cache` directory and runs:
```bash
terraform init
terraform plan   # (or apply / destroy)
```
Your `inputs = { ... }` block values are passed as `TF_VAR_*` environment variables.

## Key Concepts (Topics from Prompt)

### Units
A **unit** is a directory containing a `terragrunt.hcl` file. It is the smallest atomic deployable entity. A unit wraps one Terraform root module.

```hcl
# live/prod/app/terragrunt.hcl
terraform {
  source = "git::git@github.com:myorg/modules.git//app?ref=v1.4.2"
}

inputs = {
  instance_count = 10
  instance_type  = "m8g.large"
  environment    = "prod"
}
```

### `include` Blocks
Share common config from parent `terragrunt.hcl` files without copy-paste. The `find_in_parent_folders()` function walks up the directory tree to find the nearest matching file.

```hcl
# live/prod/app/terragrunt.hcl
include "root" {
  path = find_in_parent_folders("root.hcl")  # inherits backend, provider config
}
include "env" {
  path = find_in_parent_folders("env.hcl")   # inherits env-specific settings
}
```

### `generate` Blocks
Inject files into the Terraform working directory before `init`. The primary use case is dynamically generating `backend.tf` and `provider.tf` so they don't need to be copy-pasted into every module.

```hcl
# root.hcl (parent)
generate "backend" {
  path      = "backend.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<EOF
terraform {
  backend "s3" {
    bucket         = "my-tf-state"
    key            = "${path_relative_to_include()}/terraform.tfstate"
    region         = "ap-south-1"
    dynamodb_table = "terraform-lock"
    encrypt        = true
  }
}
EOF
}
```

`path_relative_to_include()` is a Terragrunt function that returns the relative path of the current unit from the root — making every unit's state key unique automatically.

### `dependency` Blocks
Declare that one unit depends on outputs from another. Terragrunt reads the dependent unit's remote state and exposes its outputs.

```hcl
# live/prod/app/terragrunt.hcl
dependency "vpc" {
  config_path = "../vpc"   # relative path to another unit
}

inputs = {
  vpc_id     = dependency.vpc.outputs.vpc_id
  subnet_ids = dependency.vpc.outputs.private_subnet_ids
}
```

**What breaks**: if the `vpc` unit hasn't been applied yet (its state is empty), the `dependency` block fails. Use `mock_outputs` for plan-only testing:
```hcl
dependency "vpc" {
  config_path = "../vpc"
  mock_outputs = {
    vpc_id         = "vpc-00000000"
    private_subnet_ids = ["subnet-00000000"]
  }
  mock_outputs_allowed_terraform_commands = ["validate", "plan"]
}
```

### Hooks (`before_hook`, `after_hook`)
Run shell commands before or after Terraform commands. Use cases: compliance scanning, secret injection, Slack notifications.

```hcl
terraform {
  before_hook "validate_plan" {
    commands = ["plan"]
    execute  = ["tfsec", "."]   # security scan before every plan
  }
  after_hook "notify" {
    commands     = ["apply"]
    execute      = ["slack-notify", "apply complete in ${get_env("ENV")}"]
    run_on_error = true
  }
}
```

### `run-all` — Multi-Unit Orchestration
Apply (or plan/destroy) an entire directory tree of units at once, respecting `dependency` ordering.

```bash
# From the live/prod/ directory — plans ALL units under prod/
terragrunt run-all plan

# Apply all units, but only those whose plan shows changes
terragrunt run-all apply
```

**Operational risk**: a `run-all apply` on a large environment propagates failures. If unit 3 fails (e.g., ECS service), units that depend on it are skipped, but independent units (e.g., a CloudWatch dashboard) may have already applied. The blast radius is the entire directory tree.

### Implicit vs Explicit Stacks
- **Implicit stack**: just a directory tree of units. No extra config. `run-all` discovers units by finding `terragrunt.hcl` files.
- **Explicit stack** (`terragrunt.stack.hcl`): a file that explicitly declares which units belong to the stack and their versions. Use when you want to version a collection of units and promote it across environments.

## What Terraform Guarantees vs What Terragrunt Adds

| Concern | Terraform alone | With Terragrunt |
|---|---|---|
| DRY backend config | ❌ Copy-paste per module | ✅ `generate` block in parent |
| DRY provider config | ❌ Copy-paste per module | ✅ `generate` block in parent |
| Cross-module output references | ❌ Manual `terraform_remote_state` | ✅ `dependency` blocks |
| Multi-unit orchestration | ❌ Manual ordering | ✅ `run-all` with auto dependency resolution |
| Immutable versioned modules | ⚠️ Manual discipline | ✅ `source` `?ref=` enforced per unit |

## When NOT to Use Terragrunt

- Your team is new to Terraform — learn Terraform's own mental model first, then add the wrapper
- You have a single AWS account with one environment — the DRY savings don't justify the added abstraction
- Your team can't explain what `.terragrunt-cache` is — the magic becomes confusion
- You need Terraform Cloud/Enterprise features (remote plans, policy enforcement) — Terragrunt can conflict with some of these workflows
